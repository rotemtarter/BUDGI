# MILESTONES.md — Budgi

## מטרת המסמך

מסמך זה מגדיר את אבני הדרך לפיתוח MVP של Budgi. החלוקה מבוססת על `PRD.md`, `ARCHITECTURE.md` ו-`DESIGN.md`, ומעדיפה `Vertical Slices`: בכל אבן דרך נמסרת יכולת משתמש עובדת, מקצה לקצה, שניתן לבדוק ולאשר באופן עצמאי.

יש לבצע את אבני הדרך לפי הסדר. אין להתחיל אבן דרך חדשה לפני שהמשתמש בדק ואישר במפורש את הקודמת.

## עקרונות ביצוע

1. **סדר מחייב:** יש לפתח את ה-Milestones לפי הסדר המופיע במסמך.
2. **עצירה לאישור:** בסיום כל Milestone יש לעצור, להציג למשתמש את התוצר, לפרט אילו סעיפי `Definition of Done` נבדקו ולהציג את תוצאות הבדיקות.
3. **אין מעבר אוטומטי:** אין להתחיל את ה-Milestone הבא ללא אישור מפורש של המשתמש.
4. **Database Migrations:** כל שינוי בסכמת Database ייווצר כ-SQL migration חדש ב-`supabase/migrations/`. יש להחיל ולהריץ בדיקות מול Supabase Development בלבד במהלך הפיתוח. אין לשנות את Production כחלק מעבודת Milestone רגילה.
5. **Production:** עדכון סכמת Production ופרסום הגרסה החיה יתבצעו רק במסגרת Milestone הפריסה, לאחר בדיקות ואישור מפורש.
6. **אבטחת סביבות:** אין להשתמש בנתוני משתמשים אמיתיים ב-Development, ואין להכניס Secrets ל-Git או לקוד Frontend.
7. **בדיקות:** יש להוסיף בדיקות אוטומטיות מתאימות לאורך הפיתוח באמצעות `Vitest` לבדיקות Unit/Integration ו-`Playwright` לבדיקות End-to-End.
8. **שמירה על Scope:** אין להוסיף יכולות שאינן מוגדרות ב-PRD. כאשר מסמך עיצוב חסר עבור יכולת שנדרשת ב-PRD, יש לעצור ולקבל אישור לעיצוב הנדרש לפני מימוש UI חדש.

## Milestone 1 — הקמת הפרויקט, תשתיות וסביבות

### מטרה
להקים בסיס טכני עובד ל-Budgi, כולל Repository, אפליקציית Web, סביבת פיתוח וסביבת Production נפרדות, ותהליך עבודה בטוח שמאפשר לפתח ולבדוק את שאר היכולות.

### מה יש לממש
- יצירת GitHub Repository והקמת פרויקט `Next.js` עם `App Router`, `React` ו-`TypeScript`.
- התקנת והגדרת `Tailwind CSS`, `shadcn/ui`, מבנה תיקיות לפי ה-Modules שב-Architecture, וכלי בדיקות `Vitest` ו-`Playwright`.
- הגדרת בסיס `DESIGN.md`: גופן `Plus Jakarta Sans`, צבעי המותג, RTL, רכיבי בסיס ו-Responsive layout.
- יצירת פרויקט Supabase נפרד ל-`Development` ופרויקט נפרד ל-`Production`.
- **הקמת Supabase תבוצע בהדרכה צעד אחר צעד:** ה-AI ינחה את המשתמש לפתוח את שני הפרויקטים, לבחור שמות מתאימים (למשל `budgi-dev` ו-`budgi-prod`), להעתיק את פרטי החיבור הנדרשים ולהגדיר אותם בסביבה הנכונה. אין לבקש מהמשתמש לפרסם Secrets בצ'אט או לשמור אותם ב-Git.
- הגדרת `.env.example` עם שמות משתנים וערכי Placeholder בלבד; `.env.local` מקומי יתחבר ל-Development בלבד ויוחרג מ-Git.
- הגדרת Vercel עם הפרדה בין `Preview` שמתחבר ל-Development לבין `Production` שמתחבר ל-Supabase Production. מפתחות OpenAI יוגדרו רק כאשר יידרשו ב-Milestone ה-AI.
- הגדרת Google OAuth בנפרד לכל סביבה, ככל שנדרש לתשתית ההתחברות.
- יצירת מסלול בסיסי של Build ו-Deployment, ללא פיצ'רים עסקיים.

### תוצר מצופה
- אפליקציית Budgi בסיסית עולה מקומית ונפרסת ל-Vercel Preview.
- קיימים שני פרויקטי Supabase נפרדים ומוגדרים.
- סביבת Preview מחוברת ל-Development בלבד; הגדרות Production נשמרות בנפרד ואינן משמשות בפיתוח מקומי.
- Repository, בדיקות בסיסיות ותהליך Build תקינים.

### Definition of Done
- [ ] הפרויקט נבנה בהצלחה (`build`) ללא שגיאות.
- [ ] האפליקציה נטענת מקומית ומוצגת ב-Vercel Preview.
- [ ] קיימים שני פרויקטי Supabase נפרדים: Development ו-Production.
- [ ] משתני הסביבה של Local ו-Preview מצביעים ל-Development בלבד.
- [ ] פרטי Production אינם נמצאים בקובצי Local, ב-Preview או ב-Git.
- [ ] `.env.example` קיים ואינו מכיל ערכי Secrets אמיתיים.
- [ ] `Vitest` ו-`Playwright` מוגדרים וריצת בדיקות בסיסית עוברת.
- [ ] המשתמש קיבל הסבר ברור היכן נשמרים פרטי הגישה וכיצד נשמרת ההפרדה בין הסביבות.

## Milestone 2 — התחברות, חשבון והגדרה ראשונית

### מטרה
לאפשר למשתמש להיכנס למערכת באמצעות Google, ליצור חשבון אישי לעסק אחד ולהגדיר את התקציב והיעדים הראשוניים.

### מה יש לממש
- מסכי התחברות, הרשמה ואישור הרשמה בהתאם ל-Wireframes ול-Design.
- `Supabase Auth` עם `Google OAuth`, ניהול Session ויציאה מהחשבון.
- יצירת פרופיל משתמש ונתוני עסק אישי אחד לכל חשבון.
- מסך הגדרה ראשונית להגדרת תקציב שיווק חודשי כולל, יעד הכנסות חודשי ויעד עסקי נוסף נתמך, למשל מספר עסקאות.
- הגדרות ספי התראה שהמשתמש בוחר, בהתאם לסוגי ההתראות שהוגדרו ב-PRD.
- שמירת הנתונים ב-PostgreSQL ואכיפת הפרדת משתמשים באמצעות `Row Level Security (RLS)`.
- יצירת SQL migrations עבור טבלאות המשתמש/עסק, תקציב, יעדים והגדרות התראה.

### תוצר מצופה
משתמש יכול להירשם או להתחבר, להשלים הגדרה ראשונית, לשמור את התקציב והיעדים, לצאת ולהתחבר מחדש ולראות שהנתונים נשמרו בחשבונו בלבד.

### Definition of Done
- [ ] התחברות והרשמה באמצעות Google פועלות ב-Development.
- [ ] משתמש חדש יכול להשלים הגדרה ראשונית ולשמור תקציב חודשי ויעד הכנסות.
- [ ] ניתן לשמור יעד עסקי נוסף הנתמך בנתוני המערכת.
- [ ] ניתן להגדיר ולשמור ספי התראה.
- [ ] Session נשמר ומטופל כראוי, ופעולת Logout פועלת.
- [ ] משתמש אינו יכול לקרוא או לשנות נתונים של משתמש אחר; בדיקות RLS מאמתות זאת.
- [ ] טפסים כוללים ולידציה והודעות שגיאה בעברית.
- [ ] כל SQL migrations של אבן דרך זו הורצו ונבדקו ב-Supabase Development בלבד.
- [ ] בדיקות Unit/Integration ותרחישי Playwright מרכזיים עוברים.
- [ ] אין שינוי בסכמת Production.

## Milestone 3 — ניהול קמפיינים והזנת נתונים ידנית

לאפשר למשתמש לנהל קמפיינים ולהזין עבורם את נתוני הביצועים הדרושים לחישובים ולניתוח בהמשך.

### מה יש לממש
- רשימת קמפיינים ומסך יצירה/עריכה בהתאם ל-Wireframes ול-Design.

- הגדרת תקציב מתוכנן לכל קמפיין.
- טופס הזנת נתוני ביצועים לתקופה: הוצאה בפועל, לידים, עסקאות, לקוחות חדשים והכנסות.

- SQL migrations לטבלאות קמפיינים ונתוני ביצועים, כולל קשרים, Constraints ו-RLS.

### תוצר מצופה

- [ ] כל קמפיין משויך לאחת מארבע הפלטפורמות הנתמכות.
- [ ] ניתן לשמור תקציב מתוכנן לכל קמפיין.
- [ ] ניתן להזין ולשמור הוצאה, לידים, עסקאות, לקוחות חדשים והכנסות לפי תקופה.

## Milestone 4 — ייבוא CSV/Excel ועדכון נתונים

### מטרה
לאפשר למשתמש להזין נתוני קמפיינים בכמות באמצעות קובצי CSV ו-Excel, תוך ולידציה וזיהוי נתונים קיימים כדי לצמצם כפילויות.

### מה יש לממש
- מסך ייבוא נתונים בהתאם ל-Wireframes ול-Design.
- העלאת קובץ CSV או Excel ועיבודו בצד השרת באמצעות `SheetJS (xlsx)` ו-CSV parser.
- קריאת כותרות, מיפוי עמודות לשדות הנתמכים וולידציה של שורות וערכים.
- זיהוי קמפיין ותקופה והשוואה לרשומות קיימות.
- עדכון נתונים קיימים במקום יצירת כפילויות כאשר ניתן לזהות התאמה חד-משמעית.

- חיבור הייבוא לנתוני הקמפיינים הקיימים. לאחר כתיבה מוצלחת יש להפעיל חישוב מחדש של מדדים/תחזיות ובדיקת התראות, ככל שהיכולות הרלוונטיות כבר זמינות או עם חיבורן ב-Milestone הבא.

### תוצר מצופה
משתמש יכול לייבא קובץ, להבין אילו נתונים נקלטו ואילו נדחו, ולעדכן נתונים קיימים לפי קמפיין ותקופה בלי ליצור כפילויות כאשר ההתאמה מזוהה באופן חד-משמעי.

### Definition of Done

- [ ] הקובץ מפוענח בשרת ולא נדרש חיבור API לפלטפורמות פרסום.
- [ ] נתונים עוברים ולידציה לפני שמירתם.
- [ ] התאמה חד-משמעית של קמפיין ותקופה מעדכנת רשומה קיימת במקום ליצור כפילות.
- [ ] שורות שגויות או לא מזוהות מדווחות למשתמש באופן ברור בעברית.
- [ ] קובץ לא נתמך, ריק או גדול מהמגבלה מטופל בהודעה ברורה.
- [ ] ייבוא מוצלח אינו יוצר רשומות כפולות בבדיקות חוזרות של אותו קובץ/אותה תקופה.

## Milestone 5 — מדדים, Dashboard, תחזיות והתראות

### מטרה
להפוך את נתוני התקציב והקמפיינים לתמונה עסקית שימושית: מדדים מחושבים, השוואות, תחזית חודשית והתראות שנבדקות בכל שינוי נתונים.

### מה יש לממש
- `Metrics Service` לחישוב:
  - תקציב חודשי כולל, סכום תקציבים מתוכננים לקמפיינים והפער ביניהם.
  - הוצאות בפועל, יתרת תקציב וקצב ניצול התקציב.
  - `CPL`, `Cost per Deal`, `CAC`, `ROAS`.
  - התקדמות לעבר יעד ההכנסות.
- חישובים יתבצעו בקוד באופן דטרמיניסטי ולא באמצעות LLM.
- טיפול בנתונים חסרים ובמכנה אפס: הצגת מדד כלא זמין והסבר על החוסר, ללא הצגת אפס מטעה.
- `Forecast Service` לתחזית הוצאות והכנסות עד סוף החודש על בסיס הקצב הנוכחי ומגמות היסטוריות זמינות.
- הצגת אי-ודאות או חוסר בנתונים כאשר אין בסיס לתחזית מהימנה.
- Dashboard בהתאם ל-Wireframes ול-Design: KPI cards, גרפי מגמה, טבלת השוואת קמפיינים, תקציב ותחזית.
- מסכי מדדים ותחזית בהתאם ל-Wireframes.
- `Alert Service` לבדיקת ספי התראה שהמשתמש הגדיר: קצב הוצאות, ירידה בביצועי קמפיין, התקרבות ליעד או חריגה ממנו, וחריגה משמעותית מהתקציב.
- הפעלת בדיקת התראות לאחר כל עדכון ידני ולאחר כל ייבוא נתונים.
- הצגת התראות קופצות בעת הצורך ושמירתן במרכז התראות.
- עדכון הגדרות ספי התראה דרך מסך ההגדרות.
- SQL migrations לטבלאות/שדות נדרשים עבור התראות, היסטוריה או נתונים נגזרים, ככל שנדרשים לפי המימוש.

### תוצר מצופה
משתמש יכול לפתוח Dashboard ולקבל תמונת מצב המבוססת על הנתונים שהזין או ייבא, לעיין במדדים ובתחזית, ולהציג התראות שנוצרו לאחר שינוי נתונים.

### Definition of Done
- [ ] כל המדדים המוגדרים ב-PRD מחושבים נכון לפי נתוני בדיקה ידועים.
- [ ] `CAC` מחושב לפי מספר לקוחות חדשים ולא לפי מספר עסקאות.
- [ ] תקציב כולל מושווה לסכום התקציבים המתוכננים לקמפיינים.
- [ ] חלוקה באפס ונתונים חסרים אינם מייצרים ערך שגוי; המדד מסומן כלא זמין.
- [ ] תחזית משתמשת בקצב הנוכחי ובמגמות עבר כאשר נתונים כאלה קיימים.
- [ ] כאשר אין די נתונים, המערכת מציגה מגבלה ברורה ולא תחזית ודאית.
- [ ] Dashboard, מסך מדדים ומסך תחזית מציגים נתונים התואמים לנתוני ה-Database.
- [ ] גרפים, KPI cards וטבלאות תואמים ל-`DESIGN.md` ופועלים בפריסת RTL רספונסיבית.
- [ ] שינוי נתונים ידני מפעיל בדיקת התראות.
- [ ] ייבוא נתונים מוצלח מפעיל בדיקת התראות.
- [ ] התראות נשמרות במרכז ההתראות ומוצגות גם כהודעות קופצות כאשר התנאים מתקיימים.
- [ ] ספי ההתראה ניתנים להגדרה ונשמרים למשתמש.
- [ ] בדיקות חישוב, תחזית, התראות ותרחישי Playwright עוברים.

## Milestone 6 — AI Budget Advisor

### מטרה
לאפשר למשתמש לשאול שאלות בשפה חופשית על נתוני התקציב והקמפיינים ולקבל הסברים והמלצות אופרטיביות שמבוססות על נתוני החשבון.

### מה יש לממש
- ממשק שיחה ל-`AI Budget Advisor`.
- **תנאי עיצוב לפני מימוש UI:** ב-`DESIGN.md` צוין שאין ב-Wireframes שסופקו מסך ייעודי ל-AI Budget Advisor. לפני בניית ממשק השיחה יש לקבל מהמשתמש אישור ל-Wireframe/פריסת מסך משלימה. אין להמציא מסך או רכיבים מהותיים ללא אישור.
- `AI Advisor Service` בשרת באמצעות `OpenAI API (Responses API)`.
- שליפת נתוני החשבון הרלוונטיים מ-PostgreSQL, שימוש בתוצאות `Metrics Service` ויצירת הקשר ממוקד למודל.
- ביצוע חישובים מספריים בקוד בלבד; ה-LLM אחראי לניסוח ניתוח, הסבר והמלצה על בסיס הנתונים המחושבים.
- שימוש ב-`Structured Outputs` וב-`Zod` לאימות מבנה התשובה.
- המלצות הכוללות סכום כספי ו/או אחוז שינוי כאשר ניתן לבססן, הסבר והערכת השפעה צפויה ככל שהנתונים מאפשרים.
- הצגת מגבלות, אי-ודאות ונתונים חסרים.
- כאשר אין די נתונים, ה-AI מבקש מהמשתמש להזין או לייבא את המידע החסר.
- שמירה על גבולות הרשאה: כל שיחה משתמשת רק בנתוני החשבון של המשתמש המחובר.
- הגבלת אורך הקשר/שיחה ונפח הנתונים הנשלחים ל-API, וניהול `OPENAI_API_KEY` בצד השרת בלבד.
- ה-AI מספק המלצות בלבד ואינו משנה תקציבים או מבצע פעולות בפלטפורמות פרסום.

### תוצר מצופה
משתמש יכול לשאול שאלה על נתוני העסק, לקבל תשובה מנומקת והמלצה מבוססת נתונים, ולראות בבירור כאשר המידע אינו מספיק. אין שינוי אוטומטי בתקציב.

### Definition of Done
- [ ] ממשק השיחה מומש רק לאחר אישור המשתמש לפריסת המסך החסרה.
- [ ] משתמש יכול לשלוח שאלה בשפה חופשית ולקבל תשובה.
- [ ] תשובת AI מבוססת רק על נתונים שנשלפו מהחשבון המחובר ועל מדדים שחושבו במערכת.
- [ ] חישובים מספריים אינם מתבצעים על ידי המודל אלא על ידי שירותי החישוב.
- [ ] תשובות מובנות עוברות ולידציה באמצעות `Zod` ו-`Structured Outputs`.
- [ ] המלצה כוללת סכום ו/או אחוז שינוי כאשר הנתונים מאפשרים זאת, וכן הסבר רלוונטי.
- [ ] כאשר אין די נתונים, ה-AI מציין זאת ומבקש נתונים חסרים במקום להמציא ערכים.

## Milestone 7 — הקשחה, בדיקות קצה ופריסה ל-Production

### מטרה
להשלים בדיקות מקצה לקצה של ה-MVP, לוודא אבטחה, אמינות והתאמה לעיצוב, ולהעביר את המוצר לסביבת Production באופן מבוקר.

### מה יש לממש
- בדיקות End-to-End של זרימת משתמש מלאה: התחברות, הגדרת תקציב ויעדים, יצירת קמפיין, הזנת נתונים, ייבוא, צפייה ב-Dashboard, התראות ושימוש ב-AI.
- בדיקות Responsive ב-Desktop, Tablet ו-Mobile, כולל RTL וטקסטים משולבים בעברית/אנגלית.
- בדיקות הרשאות ו-`RLS`, ולידציה, חלוקה באפס, נתונים חסרים, קבצים לא תקינים, חריגות תקציב וכשלי OpenAI/Supabase.
- בדיקת ביצועים בסיסית וזמני תגובה, טיפול בשגיאות ו-Logs באמצעות `Vercel Logs` ו-`Supabase Logs`.
- בדיקת התאמה של המסכים ל-`DESIGN.md`, ל-Wireframes ול-Mockups; אין להוסיף מסכים או פיצ'רים חדשים בשלב זה.
- הכנת Production: הגדרת Google OAuth Redirects, כתובות Auth, משתני סביבה, Secrets, חיבור Vercel ל-Supabase Production והגדרות ספקים נדרשות.
- סקירת כל ה-SQL migrations שנבדקו ב-Development והכנת סדר הרצה ל-Production.
- **עדכון Production רק לאחר אישור מפורש של המשתמש:** הרצת migrations על Supabase Production לפני פרסום קוד שתלוי בסכמה החדשה. יש לוודא שתהליך הפריסה אינו מאפשר לקוד החדש לעלות לפני שה-Migration הנדרש הושלם בהצלחה. אם נדרשת הפרדה, יש להשתמש ב-Release/Promotion מבוקר ולא להסתמך על Merge אוטומטי שיכול לפרוס מיד.
- פרסום גרסת Production ב-Vercel וחיבור לדומיין, אם הוגדר.
- בדיקת Smoke Tests לאחר הפריסה.

### תוצר מצופה
גרסת MVP יציבה ונגישה ב-Production, מחוברת לפרויקט Supabase Production, עם זרימות הליבה פעילות ועם הפרדה מלאה מסביבת Development.

### Definition of Done
- [ ] תרחישי End-to-End מרכזיים עוברים ב-Playwright.
- [ ] בדיקות Unit/Integration עוברות ללא כשל.
- [ ] נבדקה התאמה רספונסיבית ב-Desktop, Tablet ו-Mobile.

- [ ] נבדקו תרחישי נתונים חסרים, ערכים לא תקינים, חלוקה באפס וייבוא כושל.

- [ ] Logs זמינים לבדיקת תקלות.

## Development Execution Rules — כללי ביצוע הפיתוח על ידי AI

ההנחיות בסעיף זה מחייבות כל AI או גורם פיתוח שימשיך את הפרויקט:

1. יש לקרוא את `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md` ואת `MILESTONES.md` לפני תחילת העבודה.
2. יש לפתח את ה-Milestones לפי הסדר המדויק במסמך. אין לדלג על אבן דרך ואין להתחיל כמה אבני דרך במקביל.
3. בתחילת כל Milestone יש להציג למשתמש בקצרה את מטרתו, היקף המימוש והתלויות שצריכות להיות מוכנות.
4. במהלך Milestone יש לממש רק את היכולות המוגדרות בו ואת התשתיות הנחוצות להן. אין להרחיב Scope ללא אישור.
5. כל שינוי Database Schema ייעשה באמצעות SQL migration מתועד. יש להריץ ולבדוק אותו ב-Supabase Development בלבד. אין להחיל Migration על Production כחלק מפיתוח שוטף.
6. לפני כל שינוי Production, לרבות Migration או פרסום, יש לקבל אישור מפורש מהמשתמש.
7. בסיום כל Milestone יש לעצור את הפיתוח ולא להתחיל את הבא.
8. בסיום יש להציג למשתמש:
   - מה מומש ומה זמין לבדיקה.
   - רשימת סעיפי `Definition of Done` עם סטטוס לכל סעיף.
   - תוצאות בדיקות `Vitest`, `Playwright`, Build ובדיקות ידניות רלוונטיות.
   - Migrations שנוצרו והאם הורצו בהצלחה ב-Development.
   - בעיות פתוחות, מגבלות או סעיפים שלא הושלמו.
   - כתובת Preview או הוראות בדיקה, כאשר זמינות.
9. יש לבקש מהמשתמש לבדוק את התוצר ולאשר במפורש את המעבר ל-Milestone הבא.
10. אם סעיף DoD אינו מתקיים, יש לתקן אותו במסגרת אותו Milestone ולדווח מחדש. אין לסמן Milestone כהושלם על סמך קוד שנכתב בלבד.
11. אם קיימת סתירה בין המסמכים או חסר מידע מהותי שמונע מימוש נכון, יש לעצור ולשאול שאלה ממוקדת אחת במקום להמציא דרישה.
12. לאחר אישור המשתמש, יש להתחיל רק את ה-Milestone הבא ולשמור על רצף ההחלטות והבדיקות.
